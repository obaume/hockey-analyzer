# Single-table inheritance for Event subtypes, not joined-table

`Event`'s seven subtypes (`period_start`, `period_end`, `stoppage`, `faceoff`, `shot_attempt`, `penalty`, `shift_change`) are modeled as SQLAlchemy children of an abstract `Event` base, using single-table inheritance: one shared `events` table, with each subtype-specific column (e.g. `shot_x`, `penalty_infraction`) declared on its owning child class rather than on `Event` itself. We rejected joined-table inheritance, where each subtype gets its own physical table joined back to a slim `events` base — that would additionally make subtype-specific columns genuinely `NOT NULL` at the database level, which single-table inheritance doesn't (a `Penalty` row still has unused, nullable `shot_x`/`shot_type`/etc. columns sitting in the shared table). We chose to accept that DB-level nullability rather than pay joined-table's cost on every timeline query: CONTEXT.md's game-clock, shift, and stint derivations all need to iterate a game's events in `video_timestamp` order and branch on type — one query under single-table inheritance, versus a join across up to eight tables (or eight separate queries merged in Python) under joined-table.

Reversing this later, once real tagging data exists, means a genuine data migration — this was worth pinning down deliberately rather than reaching for whichever style seemed more "properly normalized" without weighing it against how the data actually gets queried.
