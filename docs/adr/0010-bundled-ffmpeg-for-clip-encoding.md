# Bundled ffmpeg (via imageio-ffmpeg) for clip encoding, stream-copying phone-ready footage

Clip export (ticket 24) has to cut segments out of a game's footage and write H.264/AAC `.mp4` files (see CONTEXT.md's **Clip**), hard-cutting several segments into one file for a **Highlight reel**. We shell out to ffmpeg for this, taking the binary from the `imageio-ffmpeg` wheel rather than asking users to install ffmpeg themselves. The wheel ships a static ffmpeg build per platform (Windows, macOS, Linux) that includes `libx264` and the native AAC encoder, so `pip install` is the whole setup, the same as every other dependency. `imageio_ffmpeg.get_ffmpeg_exe()` also honours an `IMAGEIO_FFMPEG_EXE` environment variable, so a user can point it at a different ffmpeg without a code change. Qt Multimedia, which we already depend on, can play footage but can't trim or concatenate it. PyAV would give an in-process API, but stream-copy cutting and concatenation would then be ours to write packet by packet.

The trade-offs:

- **Licensing.** The bundled ffmpeg build links `libx264`, so it's GPL. That's compatible with the repo's planned GPL-3.0 licence (see ADR-0009) and adds no new obligation.
- **Size.** The bundled binary adds about 85 MB to an install (Windows x86-64, ffmpeg 7.1).
- **No ffprobe.** Only `ffmpeg` is bundled, so `probe_footage` reads the stream description ffmpeg prints for `ffmpeg -i <file>` (duration, codecs, pixel format) instead of ffprobe's JSON. That text isn't a stable interface, and the regexes may need adjusting across ffmpeg releases. `tests/test_clip_encoder.py` runs against the real binary, so a change like that shows up as a failing test.

**Passthrough.** When the footage is already 8-bit 4:2:0 H.264 (limited- or full-range, `yuv420p`/`yuvj420p`) with AAC or no audio, we stream-copy it instead of re-encoding. This is fast, loses no quality, and every video packet in the clip is byte-identical to the source. Our tests check exactly that. A copied cut can only start on a keyframe, so each segment's start is first moved back to the keyframe at or before it (found with a single seek). Each segment is then copied into its own temporary part, and the parts are joined with ffmpeg's concat demuxer. Cutting every segment in one concat pass is simpler, but it leaves timestamps running backwards at a reel's joins. The pre-roll before an unaligned start and the B-frame tail past each end overlap the next segment, and some phone players stutter on that. The cost is that a clip can begin up to one keyframe interval before its **Padding window** and run a fraction of a second past it. Real camera footage typically has a keyframe every 1–2 s, while the default window already has 5 s of lead-in, so this is an accepted imprecision. Any other footage is fully re-encoded with frame-accurate cuts (libx264, CRF 20, `yuv420p`, AAC 160 kb/s, `+faststart`). Footage that is H.264 but has, say, MP3 audio is also fully re-encoded rather than copying the video and re-encoding only the audio. That case is rare enough that it isn't worth a third code path.
