# League game-link import scrapes the PDF export, not the HTML pages, as its primary source

Ticket 02's investigation found the league site's game and roster data via two separate HTML pages (`game/{id}`, `game/aufstellung/{id}`), scraped by CSS class. While designing ticket 11's import flow, we found the site also exposes a server-generated PDF (`GET .../GameCenter/GameDetail/ExportGameTimeline?gameId={id}`, unauthenticated aside from a `Referer` check) that bundles game metadata, final and period-by-period score, and both teams' full lineups in a single fetch — a superset of what the two HTML pages provide between them, in one document instead of two. We decided to make this PDF the primary source for game metadata and roster import, rather than the HTML pages ticket 02 originally investigated.

The one thing the PDF lacks that the HTML game-overview page has is each team's stable composite `league_id`. Since that ID is the primary team-matching key the roster/team data model relies on (ticket 04), the import still makes one extra HTML fetch (`game/{id}`) solely to recover it — so the import ends up depending on both sources, each independently fallback-able (a failure in one degrades only what that source was responsible for, not the whole import).

Rejected alternative: staying HTML-only, as ticket 02 originally scoped, would have avoided depending on a second source shape entirely, but would mean parsing two separate CSS-class-scraped pages (each independently redesign-fragile) to reconstruct data the PDF already presents as one coherent, purpose-built export — plus doing without the score, which the HTML roster/overview pages don't expose as cleanly as the PDF's dedicated score line.
